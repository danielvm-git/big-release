Versioning

big-release uses Semantic Versioning (SemVer) to communicate changes to your users:

MAJOR.MINOR.PATCH

Version numbers

ComponentWhen to bumpExample
MAJORBreaking changes (incompatible API changes)2.0.0
MINORNew features (backward-compatible)1.3.0
PATCHBug fixes (backward-compatible)1.2.1

How big-release calculates versions

big-release analyzes all commits since the last release and applies these rules:

  1. If any commit has BREAKING CHANGE or feat! → bump MAJOR
  2. Else if any commit is feat: → bump MINOR
  3. Else if any commit is fix: or perf: → bump PATCH
  4. Else → no release

First release

For the first release, big-release uses the initialVersion from your configuration. If not set, it defaults to 1.0.0.

# .big-release.yml
initialVersion: "0.1.0"

Tip: Start at 0.1.0 for new projects. This signals that the project is still in development and the API may change.

Prereleases

big-release supports prerelease versions for testing before stable releases:

# First prerelease: 1.0.0-alpha.0
# Second prerelease: 1.0.0-alpha.1
# Stable release: 1.0.0
Quick check

If the current version is 1.3.2 and you push a commit with BREAKING CHANGE, what is the next version?

{{ q1.feedbackText }}

Version calculation examples

# Commits since last release:
feat(auth): add OAuth2
fix(api): handle null
docs: update readme

# Calculated version: 1.1.0 (feat takes precedence over fix)
# docs: does not trigger a release
# Commits since last release:
fix(api): handle timeout
chore: update deps

# Calculated version: 1.0.1 (fix triggers PATCH)
# chore: does not trigger a release
